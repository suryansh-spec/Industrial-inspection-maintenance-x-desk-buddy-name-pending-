# Dual-Mode AI Inspection & Desk Companion

**Version:** 2.0  
**Date:** November 2026  
**Product Type:** Portable Embedded AI Device  
**Primary Controller:** ESP32  
**AI Architecture:** Cloud-based AI inference with local sensor acquisition  
**Operating Modes:** Industrial Inspection Mode and Desk Buddy Mode  
**Status:** Product Specification / Development Baseline

# 1. Product Overview

## 1.1 Product Vision

Develop a portable, intelligent, dual-purpose electronic device that combines industrial inspection capabilities with a personal desktop companion.

The device will operate in two independent modes:

1. **Industrial Inspection Mode:** A handheld measurement and inspection instrument capable of collecting vibration, acoustic and environmental data from physical equipment and using cloud-based AI/ML systems to identify abnormal operating patterns.
2. **Desk Buddy Mode:** An interactive desktop companion providing music control, calendar management, notifications, PC monitoring, environmental information, productivity tools and a conversational AI assistant.

Both modes will operate on the same hardware platform and share common system services.

A dedicated physical button will allow instant switching between the two modes without rebooting the ESP32.

The device will use the ESP32 for sensor acquisition, hardware control, display management and communication. Computationally intensive AI inference and external application integrations will run through a Python desktop bridge and cloud services.

## 1.2 Core Design Philosophy

The product must follow these principles:

- One physical device, two distinct operating experiences.
- No reboot required when switching modes.
- Sensor acquisition must remain reliable even when UI and network operations are running.
- AI inference should run in the cloud or on the connected computer rather than being forced onto the ESP32.
- The system should remain useful when internet connectivity is unavailable.
- Hardware and software must be modular enough to accommodate future sensors and camera integration.
- Industrial measurements must be based on actual sensor data and validated signal-processing methods, not LLM-generated assumptions.
- The assistant must operate through controlled tools rather than unrestricted system access.

## 1.3 Product Goals

| Goal | Description |
|---|---|
| Dual-purpose functionality | Combine inspection instrumentation and desktop assistance |
| Portability | Operate using an internal rechargeable battery |
| Real-time interaction | Provide responsive display, buttons and voice interaction |
| Intelligent inspection | Analyze vibration and acoustic patterns using ML |
| Desktop integration | Communicate with the user's Windows PC |
| Conversational interface | Use NVIDIA Nemotron as the assistant's language-model backend |
| Expandability | Support future camera and additional sensor modules |
| Reliability | Maintain stable operation during mode transitions and network failures |

## 1.4 Non-Goals

The initial product is not intended to be:

- A certified industrial vibration analyzer.
- A calibrated sound pressure level meter.
- A certified predictive-maintenance instrument.
- A universal defect-detection system for every machine.
- A fully autonomous industrial safety system.
- A standalone device capable of running large language models locally.
- A replacement for a full desktop computer.
- A continuous 4K video inspection system.

These capabilities may be investigated in future versions but must not be claimed without appropriate hardware, validation and datasets.

# 3. Operating Mode Management

## 3.1 Mode Definitions

The system will have exactly two primary operating modes:

- `INDUSTRIAL_INSPECTION`
- `DESK_BUDDY`

Each mode will have its own application logic, screen layout and background tasks.

Shared drivers and services will be managed centrally.

## 3.2 Physical Mode Switching

A dedicated physical button will switch between operating modes.

### Functional Requirements

| ID | Requirement | Priority |
|---|---|---|
| MODE-001 | A short press must switch the active mode. | P0 |
| MODE-002 | Mode switching must not reboot the ESP32. | P0 |
| MODE-003 | The new mode must display its home screen after switching. | P0 |
| MODE-004 | Wi-Fi connectivity must persist during transitions. | P0 |
| MODE-005 | Shared peripheral drivers should remain initialized. | P0 |
| MODE-006 | Mode-specific background tasks must be stopped or suspended safely. | P0 |
| MODE-007 | The currently selected mode must be persisted across power cycles. | P1 |
| MODE-008 | The device must visually indicate the active mode. | P1 |
| MODE-009 | An active measurement must not be silently discarded. | P0 |

### Mode Transition Sequence

```text
Physical Button Press
        |
Button Debouncing
        |
Enter MODE_TRANSITION
        |
Stop New Mode-Specific Actions
        |
Finish or Save Active Measurement
        |
Release Exclusive Audio Resources
        |
Stop Old Mode Tasks
        |
Update Active Mode
        |
Initialize / Resume New Mode Tasks
        |
Render New Home Screen
        |
Return to READY
```

The transition must be non-blocking wherever possible.

If an inspection measurement is active, the firmware should finish the current measurement window or preserve the partial data with an explicit incomplete flag.

## 3.3 Firmware State Management

Operating mode and activity state must be independent.

Suggested implementation:

```cpp
enum DeviceMode {
    INDUSTRIAL_INSPECTION,
    DESK_BUDDY
};

enum DeviceState {
    BOOTING,
    READY,
    MODE_TRANSITION,
    INSPECTION_RUNNING,
    VOICE_LISTENING,
    VOICE_PROCESSING,
    PLAYBACK,
    ERROR
};
```

Example:

```text
Active Mode: DESK_BUDDY
Device State: VOICE_LISTENING
```

This separation prevents unnecessary complexity when multiple activities are introduced.

## 3.4 Shared Services

The following services must be available independently of the active mode:

- Display Manager
- Button Manager
- Wi-Fi Manager
- Time Manager
- Sensor Manager
- Audio Manager
- Battery Manager
- Cloud Communication Client

# 4. MODE A — INDUSTRIAL INSPECTION MODE

# 4.1 Overview

Industrial Inspection Mode transforms the device into a portable, handheld condition-monitoring and equipment-inspection instrument.

The device will collect vibration and acoustic measurements from physical equipment and combine them with environmental context.

The acquired data will be processed locally for basic signal features and transmitted to a computer or cloud service for advanced analysis.

The primary objective is to demonstrate an extensible AI-powered inspection platform capable of identifying deviations from normal operating behaviour.

## 4.2 Primary Use Cases

- Inspecting small motors.
- Monitoring rotating equipment.
- Detecting unusual vibration patterns.
- Comparing healthy and abnormal operating conditions.
- Recording machine acoustic signatures.
- Identifying deviations from a recorded baseline.
- Collecting environmental conditions alongside measurements.
- Storing inspection history.
- Generating AI-assisted inspection summaries.

The first version should prioritize rotating machinery and controlled laboratory demonstrations rather than claiming universal industrial applicability.

## 4.3 Inspection Workflow

```text
Enter Industrial Mode
        |
Select Inspection Type
        |
Connect / Verify Probe
        |
Check Sensor Status
        |

        |

        |
Upload Measurement
        |
```

## 4.4 Inspection Types

### A. Vibration Inspection

**Primary sensor:** ADXL345.

The ADXL345 will be used as the primary vibration acquisition sensor.

The sensor will be mounted on a detachable probe designed to establish consistent mechanical contact with the equipment being inspected.

#### Requirements

| ID | Requirement | Priority |
|---|---|---|
| VIB-001 | Acquire three-axis acceleration data. | P0 |
| VIB-002 | Support configurable sampling frequency. | P0 |
| VIB-003 | Support configurable measurement range. | P0 |
| VIB-004 | Capture fixed-duration measurement windows. | P0 |
| VIB-005 | Calculate basic statistical features. | P0 |
| VIB-006 | Calculate frequency-domain features. | P1 |
| VIB-007 | Detect clipping and invalid measurements. | P0 |
| VIB-008 | Associate measurements with equipment profiles. | P1 |
| VIB-009 | Store and upload measurement records. | P0 |
| VIB-010 | Display acquisition and sensor status. | P0 |

#### Initial Configuration

| Parameter | Initial Value |
|---|---|
| Sensor | ADXL345 |
| Axes | X, Y, Z |
| Initial sample rate | 1 kHz |
| Measurement duration | 5 seconds |
| Initial range | ±2g |
| Communication | I2C |
| Probe connection | Detachable four-wire connection |

These values are starting configurations for prototyping, not universal measurement settings. Sampling rate, range and duration must be configurable.

#### Probe Design

The probe will contain:

- ADXL345 breakout board.
- Rigid mounting plate or block.
- Four-wire cable.
- Connector.
- Magnetic base or mechanical mounting adapter.

The sensor must be mechanically coupled to the equipment under test.

The probe must not rely on hand-held positioning during actual measurements.

A magnetic mounting arrangement may be used for ferromagnetic surfaces. A clamp or suitable adhesive adapter will be needed for nonmagnetic surfaces.

#### Signal Processing

The firmware or desktop bridge should calculate:

**Time-domain features**
- Mean.
- Standard deviation.
- RMS acceleration.
- Peak acceleration.
- Peak-to-peak amplitude.
- Crest factor.
- Kurtosis.

**Frequency-domain features**
- FFT.
- Dominant frequency.
- Spectral energy.
- Frequency-band energy.
- Spectral entropy.

The system should retain raw measurement data where storage and transfer constraints permit.

#### Interpretation

The system should initially compare measurements against recorded healthy baselines.

Potential abnormal patterns include:

- Increased vibration amplitude.
- Changed dominant frequency.
- Unexpected frequency-band energy.
- Increased impulsiveness.
- Changes in statistical distribution.

The system must not automatically label every unusual pattern as a specific mechanical fault.

Fault identification requires appropriate operating context, reference data and validation.

### B. Acoustic Inspection

**Primary sensor:** INMP441.

The INMP441 microphone will capture acoustic signatures from equipment.

The purpose is comparative acoustic analysis rather than certified sound-level measurement.

#### Requirements

| ID | Requirement | Priority |
|---|---|---|
| AUD-001 | Capture digital microphone audio through I2S. | P0 |
| AUD-002 | Support configurable recording duration. | P0 |
| AUD-003 | Support mono audio acquisition. | P0 |
| AUD-004 | Generate waveform and spectral representations. | P0 |
| AUD-005 | Calculate acoustic features. | P1 |
| AUD-006 | Upload recordings or extracted features. | P0 |
| AUD-007 | Associate recordings with equipment profiles. | P1 |
| AUD-008 | Prevent speaker output from contaminating measurements. | P0 |
| AUD-009 | Validate recording quality. | P0 |

#### Initial Audio Configuration

| Parameter | Initial Value |
|---|---|
| Microphone | INMP441 |
| Interface | I2S |
| Sample rate | 48 kHz |
| Channels | Mono |
| Capture duration | 5–10 seconds |
| Processing | FFT, PSD, spectrogram |

The microphone's actual I2S slot format and ESP32 data handling must be verified during implementation.

#### Acoustic Processing

Potential processing features:

- RMS audio amplitude.
- Peak amplitude.
- Frequency spectrum.
- Power spectral density.
- Spectrogram.
- MFCC features.
- Spectral centroid.
- Spectral bandwidth.
- Spectral roll-off.

The system may use these features to compare normal and abnormal acoustic signatures.

#### Limitations

The INMP441 is suitable for experimental acoustic anomaly detection but is not a calibrated industrial measurement microphone.

The system must not claim precise absolute dB SPL measurements without calibration.

The microphone should be positioned consistently during comparisons. Ambient noise, distance, equipment load and machine speed must be considered.

## 4.7 AI/ML Inspection Engine

The inspection engine will run outside the ESP32.

### Processing Architecture

```text
Sensor Data
    |
Data Validation
    |
Signal Preprocessing
    |
Feature Extraction
    |
Baseline Comparison
    |
ML Inference
    |
Anomaly Score
    |
Inspection Summary
```

### Initial ML Strategy

The development process should begin with interpretable baseline methods.

**Stage 1 — Statistical analysis**
- Threshold-based deviation.
- Baseline RMS comparison.
- Frequency-spectrum comparison.

**Stage 2 — Classical ML**
- Isolation Forest.
- Random Forest.
- Support Vector Machine where appropriate.

**Stage 3 — Deep Learning**
- Autoencoders.
- CNN-based spectrogram classification.
- Temporal models when sufficient sequential data exists.

The selection of models must depend on the dataset and the target inspection problem.

### Analysis Output

An inspection result should include:

- Measurement ID.
- Equipment ID.
- Overall status.
- Anomaly score, if supported.
- Important deviations.
- Relevant frequency components.
- Data-quality warnings.
- Model version.
- Timestamp.
- Suggested follow-up inspection.

Example statuses:

- Normal relative to baseline.
- Unusual behaviour detected.
- Measurement quality insufficient.
- Insufficient reference data.
- Analysis unavailable.

The system must distinguish an anomaly from a confirmed mechanical fault.

### Role of Nemotron in Inspection Mode

Nemotron may be used to explain inspection results in natural language.

For example:

- Explain why a vibration measurement differs from baseline.
- Summarize a recorded inspection.
- Explain the meaning of RMS or kurtosis.
- Describe potential causes of an observed frequency change.

Nemotron must receive actual measurement results and model outputs.

It must not independently invent sensor readings, anomaly scores or confirmed equipment diagnoses.

| BAT-004 | Display charging status where available. | P1 |
| BAT-005 | Estimate remaining runtime where sufficient data exists. | P2 |

For the proposed 3S1P battery pack:

- Nominal voltage: approximately 10.8–11.1V.
- Fully charged voltage: 12.6V.
- Capacity: 3000mAh.
- Energy: approximately 32.4–33.3Wh, depending on nominal cell voltage.

The battery percentage must not be calculated from a simplistic linear voltage mapping alone.

A calibrated discharge curve and, preferably, current integration should be used.

The proposed 3S battery pack requires an appropriate protection and balancing circuit and a dedicated 12.6V CC/CV charging solution.

The BMS is not a battery charger.

The ESP32 and peripheral electronics must receive regulated power. The battery pack must never be connected directly to 5V-rated peripherals.

# 6. VOICE ASSISTANT — SHARED AI SUBSYSTEM

## 6.1 Objective

Implement a voice-controlled assistant using NVIDIA Nemotron as the primary language-model backend.

The assistant should allow users to interact with the device naturally and execute supported actions through a controlled tool system.

The assistant is a shared subsystem and may be available in both operating modes.

## 6.2 AI Architecture

The assistant consists of four separate components:

1. Speech-to-Text.
2. Language Model.
3. Tool Execution.
4. Text-to-Speech.

Nemotron provides the language-model component. It does not eliminate the need for speech recognition and speech synthesis.

### Pipeline

```text
             USER VOICE
                  |
             INMP441
                  |
           ESP32 I2S Capture
                  |
              Wi-Fi
                  |
         PYTHON DESKTOP BRIDGE
                  |
             SPEECH-TO-TEXT
                  |
             TEXT TRANSCRIPT
                  |
          NVIDIA NEMOTRON API
                  |
          INTENT / TOOL SELECTION
                  |
            TOOL REGISTRY
                  |
          ACTION EXECUTION
                  |
           RESPONSE GENERATION
                  |
             TEXT-TO-SPEECH
                  |
             AUDIO RESPONSE
                  |
              ESP32 I2S
                  |
          MAX98357A AMPLIFIER
                  |
                SPEAKER
```

## 6.3 Voice Activation

### Initial Release: Push-to-Talk

A dedicated physical button will initiate recording.

Workflow:

1. User presses the voice button.
2. Device displays listening status.
3. ESP32 captures a bounded recording.
4. Recording stops when the button is released or the configured limit is reached.
5. Audio is transferred to the Python bridge.
6. STT produces a transcript.
7. Nemotron processes the transcript.
8. The assistant responds or requests an approved tool.
9. TTS produces audio.
10. ESP32 plays the response.

Wake-word detection is a future enhancement.

## 6.4 Assistant Capabilities

### Desk Buddy Commands

Examples:

- "Play my music."
- "Pause the music."
- "Skip this track."
- "Show me the lyrics."
- "What's my next meeting?"
- "Set a timer for 20 minutes."
- "What's the temperature?"
- "How much battery is left?"
- "What's my GPU utilization?"

### Industrial Inspection Commands

- "Explain the anomaly score."
- "Summarize this inspection."

Industrial commands must invoke validated inspection workflows and retrieve actual sensor or model data.

### Music Tools

- `music_get_lyrics`

- `get_calendar`

### Device Tools

### PC Tools

- `get_pc_status`

### Inspection Tools

- `start_vibration_measurement`

Each tool must have:

- Input validation.

- Execution timeout.

The LLM must never execute arbitrary shell commands or unrestricted Python code.

Actions with meaningful consequences, such as changing or deleting user data, should require confirmation.

## 6.6 Conversation Context

The bridge should maintain short-term conversational context.

Example:

User: "What's my GPU temperature?"

Assistant: "Your GPU is currently at 64°C."

User: "And its utilization?"

The assistant should understand that "its" refers to the GPU.

Context should be bounded and managed to avoid unnecessary token usage.

The assistant should not require continuous transmission of all sensor measurements.

## 6.7 STT and TTS Provider Architecture

STT and TTS must be independent services.

The initial implementation should use provider-independent interfaces.

Suggested abstractions:

```python
class SpeechToTextProvider:
    def transcribe(self, audio):
        pass

class TextToSpeechProvider:
    def synthesize(self, text):
        pass
```

This allows the speech provider to change without redesigning the ESP32 firmware or Nemotron integration.

The initial version should use push-to-talk recordings rather than requiring continuous live streaming.

For real-time streaming speech recognition, a dedicated streaming ASR service would be needed.

## 6.8 Assistant Availability

The assistant must distinguish between:

- Device-local functions.
- Desktop bridge functions.
- Cloud-dependent functions.

If internet connectivity fails, the device should continue basic local functions such as clock display, timers and sensor acquisition.

The device should clearly communicate when cloud AI or desktop integration is unavailable.

# 9. POWER MANAGEMENT

## 9.1 Battery Architecture

The proposed battery configuration is three compatible 18650 cells in series.

This is a 3S1P configuration.

| Parameter | Value |
|---|---|
| Number of cells | 3 |
| Configuration | 3S1P |
| Cell capacity | 3000mAh |
| Nominal pack voltage | 10.8–11.1V |
| Fully charged voltage | 12.6V |
| Pack capacity | 3000mAh |
| Approximate energy | 32.4–33.3Wh |

Series connection increases voltage, not capacity.

The three cells must be compatible in chemistry, model, capacity, age and condition.

## 9.2 Power Requirements

The battery subsystem must include:

- Appropriate 3S BMS with balancing and protection.
- Dedicated 12.6V CC/CV charger.
- Fuse close to pack positive.
- Regulated 5V supply.
- Appropriate 3.3V regulation.
- Battery voltage/current monitoring.
- Physical battery protection.

The BMS must not be treated as the charger.

The final 5V regulator must be selected based on measured peak current and thermal performance. The prototype LM2596 module must not be assumed to provide its advertised maximum current continuously.

## 9.3 Power Modes

Suggested power behaviour:

**Externally powered**
- Display can remain active.
- Normal dashboard updates.
- Normal connectivity.

**Battery powered**
- Display brightness may be reduced.
- Background polling should be optimized.
- Motion-based wake can be used.
- Network updates should be rate-limited where practical.

**Low battery**
- Display warning.
- Reduce nonessential activity.
- Preserve active measurements.
- Avoid abrupt shutdown where possible.

## 9.4 Runtime Measurement

Battery runtime must be determined through actual power measurements.

The system should not display a precise remaining runtime until a sufficiently reliable estimation method is implemented.

# 20. FINAL PRODUCT DEFINITION

The final product is a portable embedded AI platform with two primary operating experiences.

**Industrial Inspection Mode** provides sensor-based equipment monitoring, vibration and acoustic data acquisition, environmental context, anomaly detection and AI-assisted inspection summaries.

**Desk Buddy Mode** provides a compact desktop companion with music control, calendar, alarms, PC monitoring, environmental information, notifications and conversational voice interaction.

The ESP32 acts as the central hardware controller. The Python desktop bridge connects the device to desktop applications and cloud services. NVIDIA Nemotron acts as the language-model backend for the voice assistant. Dedicated ML and signal-processing pipelines remain responsible for inspection analysis.

The architecture must remain modular, support non-rebooting mode transitions and allow future camera-based inspection capabilities.

**The defining product principle: one physical device, two independent modes, one shared hardware platform, and a modular cloud-connected intelligence layer.**
